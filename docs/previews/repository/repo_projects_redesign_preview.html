一、先补上缺的“味道”：Projects 是工作台，不是资料页

如果只做项目列表、接口状态和说明卡片，页面会像“仓库信息子页”；GitHub Projects 的感觉来自“我正在一个可保存视图的工作台里推进事情”。

为什么之前会差一点感觉？

因为方案覆盖了功能点，却没有突出 GitHub Projects 的三个核心心智：保存视图、条目流动、工作上下文。移动端不一定要复制复杂交互，但必须让用户感到自己进入了一个项目工作区。

不是“项目说明页”进入后应立即看到当前视图和待处理条目，而不是先读一堆诊断字段。
不是“字段浏览器”字段只服务条目卡片、表格行和详情抽屉，不要成为页面主体。
不是“桌面端缩小版”手机端应该突出切换视图、查看条目、轻量推进，而不是复刻配置面板。

新的页面气质

  • 标题区强调“当前项目 + 当前视图”，让用户知道自己在工作台里。
  • 列表页只负责找项目；详情页才进入看板、表格、路线图工作区。
  • 条目卡片要像任务，而不是像 API 数据行：标题、状态、负责人、更新时间即可。
  • 操作按钮围绕“推进工作”：打开条目、更新状态、添加条目；低频设置放入右上角更多菜单。
  • 诊断、权限、接口信息只在异常时出现，不抢主流程。

三、项目使用流程对标

按用户的真实路径组织移动端：先找到项目，再进入工作区，再处理条目。

1. 从仓库项目标签进入

默认展示仓库关联项目列表；只有未启用、无权限或接口失败时才进入诊断空态。

2. 浏览项目列表

保留开放/已关闭切换、关键字搜索、最近更新排序、新建项目；刷新、复制链接和项目设置放到右上角更多菜单。

3. 打开单个项目工作区

进入项目后先看到项目标题、状态、更新时间和当前视图，再切换看板、表格、路线图。

4. 处理项目条目

点击卡片或表格行后打开条目详情抽屉，提供打开议题/拉取请求、复制链接、更新状态等轻量动作。

移动端保留与取舍

  • 保留：项目列表、筛选排序、视图切换、条目详情、复制链接、右上角更多菜单。
  • 轻量支持：新增条目、更新状态/优先级、关闭或重新打开项目。
  • 暂不复刻：字段配置、视图配置、自动化规则、复杂批量编辑。
  • 异常处理：无权限、接口失败、未启用项目时展示原因，并提供刷新、重新授权或稍后重试。

这样更像 GitHub Projects 的真实使用流程，而不是把接口字段摊平成说明卡。

五、项目功能流程与移动端映射

这里不再重复字段清单，而是把项目管理动作映射成手机上应该保留的流程。

用户动作移动端保留首版取舍
进入仓库项目仓库标签页直接进入项目列表诊断信息只在异常状态出现
切换开放/已关闭顶部筛选胶囊 + 最近更新排序复杂查询语法后置
打开项目工作区标题、状态、更新时间、视图切换不在列表页展示字段细节

请求编排

先加载仓库项目开关与权限，再加载项目列表；进入详情页时再请求视图和条目，避免列表页过重。

缓存策略

列表和详情摘要可缓存，页面进入先展示旧数据，再后台刷新并标注更新时间。

异常处理

无权限、未启用、无项目、网络失败分别给出不同动作，而不是统一“暂无内容”。

六、验收标准与风险清单

把预览方案转成可验证结果，方便后续拆分问题单或直接实现。

体验验收

  • 从仓库项目标签进入后，用户能直接看到项目列表或明确的异常原因。
  • 开放/已关闭、搜索、排序、新建项目、右上角更多菜单这些动作都在列表页可达。
  • 打开项目后能在看板、表格、路线图之间切换，并能继续打开条目详情。
  • 条目详情只展示必要动作，不在页面上重复铺满字段说明。
  • GraphQL 不可用时页面不崩溃，仍展示诊断说明、缓存数据与重试入口。

复杂能力边界

  • 字段配置、视图配置、自动化规则、批量编辑不做移动端首版复刻。
  • 字段值读取只服务看板卡片、表格行和条目详情，不单独做字段堆叠展示。
  • 列表页只展示条目数、视图数、更新时间，避免重复堆叠底层配置统计。
  • 写操作先控制在新增条目、更新状态/优先级、关闭或重新打开项目。
  • 遇到权限不足或冲突时，优先提示原因，并保留草稿、重试或重新授权入口。
推荐决策

把首版定位成“移动端项目浏览与轻操作工作流”，而不是“GitHub 项目全量配置器”。这样更接近项目管理真实流程，也更适合手机使用。

七、可实施路线与功能边界

下面是建议真正落代码时的阶段划分，避免一开始就被 GitHub 项目 v2 的 GraphQL 复杂度卡住。

阶段 1：当前页面立即可做

  • 保留仓库 has_projects 开关诊断。
  • 优化空态：启用状态、权限、默认分支、可见性、刷新时间。
  • 增加右上角更多菜单：刷新、复制链接、项目设置。
  • 增加开启/关闭项目功能的确认弹窗和成功/失败反馈。

阶段 2：项目列表

  • 接入 GitHub 项目 v2 GraphQL：仓库关联项目列表。
  • 列表展示标题、描述、开放/已关闭状态、更新时间、条目数。
  • 支持开放/已关闭筛选、搜索关键字、最近更新排序。
  • 没有 GraphQL 权限时降级为缓存、重试和诊断卡片。

阶段 3：项目详情只读

  • 展示项目标题、描述、状态、链接和更新时间。
  • 读取视图、字段、条目，先做看板 / 表格 / 路线图只读预览。
  • 条目点击跳转议题 / 拉取请求 / 草稿条目详情。
  • 保留右上角更多菜单处理项目设置、复制链接和关闭 / 重开。

阶段 4：轻量编辑

  • 新增条目：从议题、拉取请求或文本草稿添加。
  • 更新单选字段，如状态、优先级。
  • 关闭/重新打开项目。
  • 自动化、复杂视图配置进入项目设置或后续迭代。

九、移动端主工作台能力分层

移除外部页面依赖后，项目页按“主流程直接可用、复杂操作原生重设计、低频能力右上角收纳”三层组织。

主流程直接可用

  • 仓库项目列表：开放 / 已关闭、搜索、排序、刷新、复制项目链接。
  • 项目详情浏览：标题、描述、状态、更新时间、视图列表、字段摘要。
  • 条目工作流：查看 Issue / PR / Draft 条目，打开详情，复制链接。
  • 轻量推进：修改状态、优先级、负责人、迭代、里程碑、截止日期。
  • 新增条目：从仓库 Issue / PR 搜索添加，或创建 Draft item。
  • 项目状态管理：关闭 / 重新打开项目，编辑标题与描述。

移动端重设计

  • 看板拖拽：改为“更改状态”底部弹窗，避免横向滚动和拖动手势冲突。
  • 表格编辑：不做单元格内编辑，改为点击行后在详情页编辑字段。
  • 筛选语法：保留可视化筛选器，后续再支持 GitHub 高级查询文本。
  • 字段编辑：常用字段用原生选择器；复杂字段配置进入项目设置。
  • 批量操作：用长按多选 + 底部操作栏，减少顶部工具拥挤。
  • 通知与活动：条目详情内展示最近活动、评论入口和更新时间。

右上角更多菜单

  • 刷新项目、复制链接、分享项目。
  • 项目设置、编辑标题与描述、关闭 / 重开项目。
  • 同步状态、重试失败操作、查看权限说明。
  • 字段配置、视图配置、自动化规则作为后续原生设置页逐步补齐。

十二、产品规格补齐：完成定义

下面这组规则可以作为后续实现 RepositoryProjectsFragment / ProjectDetailFragment 时的验收口径。

App 内必须闭环

  • 列表页支持开放/关闭、搜索、排序、刷新、创建项目、关闭/重开项目。
  • 详情页支持保存视图切换、看板/表格/路线图、条目详情、活动摘要。
  • 条目支持新增 Issue/PR/Draft，更新状态、优先级、负责人、迭代、里程碑、截止日期。
  • 批量模式支持多选后统一改状态、负责人、优先级和迭代。
  • 所有写操作都有提交中、成功、失败、重试、撤销或草稿保留状态。

移动端特有优化

  • 看板拖拽改为底部状态选择，避免横向滚动和拖动手势冲突。
  • 表格单元格编辑改为条目详情字段列表，保证可触达与可撤销。
  • 高级筛选先做可视化条件，输入框只作为“搜索标题/编号/链接”。
  • 项目视图本地记忆最后一次选择，弱网下先显示缓存并后台刷新。
  • 右上角更多菜单只收纳低频能力，不替代主流程按钮。

GitHub API 落地关注点

  • Projects v2 主要依赖 GraphQL：projectV2、items、fields、views、updateProjectV2ItemFieldValue。
  • 列表、视图、字段和值要转换成稳定 ProjectUiModel，UI 不直接绑定 GraphQL 节点。
  • 权限不足、字段类型不支持、节点被删除、分页未加载完都要有显式 UI 状态。
  • 写操作需要乐观更新 + 回滚策略，避免用户以为已经同步。
  • 复杂设置先进入右上角项目设置，再按优先级逐步补齐原生页面。
更新后的结论

目标是“日常项目管理默认在 App 完成”。刷新、复制、设置、关闭 / 重开等低频动作收纳到右上角更多菜单；条目推进、筛选、编辑、协作和失败恢复保留在主流程内。

体验链路App 内完成方式恢复策略
找项目列表、搜索、开放/关闭、最近更新缓存 + 刷新重试
看进度保存视图、看板、表格、路线图GraphQL 失败显示上次缓存
推进条目详情页字段编辑、批量操作、新增条目同步队列 + 重试/撤销
