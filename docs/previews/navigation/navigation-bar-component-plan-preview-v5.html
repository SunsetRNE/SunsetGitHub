Spec v5 · Implementation Blueprint

把前四版收束成一份可开工蓝图

前面几版分别补了方向、物理组件、变体、运行时。但它们还缺一个“工程落地总图”：现有代码怎么迁、每一步交付什么、怎么验收、失败怎么回滚、最后长什么样。

v5 的目标不是再增加概念，而是把方案压成可以进入实现的路线图。

现状映射实施里程碑验收ADR

Current

MainActivity owns nav container
NavigationBarHostController mixes state and rendering calls
Renderer mutates Fragment root padding
MenuBinder directly rewrites BottomNavigationView

Target

MainActivity owns AppNavigationBarHost only
Host produces AppNavigationBarState
Planner produces RenderPlan + Insets
AppNavigationBarLayout commits pixels and events

一、当前代码到目标组件的映射

当前文件 / 职责目标归宿迁移方式保留风险
MainActivity: navViewContainer / navViewDivider / navViewAppNavigationBarLayout替换 XML 为单组件，Activity 只绑定 Host切换布局时可能影响 AppBar/NavHost constraint
NavigationBarHostControllerAppNavigationBarHost保留导航事件处理，移除直接 render/menu 操作仓库 BottomSheet 回调要保持不变
NavigationDestinationRegistryDestinationPolicy + RepositorySectionPolicy先复制为 policy，旧 registry 暂留适配遗漏 destination 会导致底栏隐藏
NavigationBarControllerRenderPlanner + AppNavigationBarLayout commit把视觉参数先转为 RenderPlan，再由 View 应用content padding 从直接 mutation 迁到 inset applier
MainNavigationMenuBinderMainMenuModelFactory + MenuRenderer先保留 BottomNavigationView，抽出 item model选中态回调要防止递归
RepositoryNavigationMenuBinderRepositoryMenuModelFactory + MenuRenderer加入未钉选当前分区临时入栏规则More 不能抢高亮
RepositoryNavigationPreferenceStore继续保留作为 repository menu model 的输入不在本轮修改存储格式

六、风险与回滚

风险表现缓解回滚点
XML 根布局变化NavHost 尺寸、AppBar inset 异常单独提交 XML 替换，截图比对恢复 activity_main.xml 与旧 binding
Inset 迁移内容遮挡或底部抖动目标态一次性发布 inset，不跟随动画帧临时回到旧 padding 逻辑
仓库参数丢失分区跳转失败或菜单退回主导航Policy 单测覆盖 owner/repo/full_name保留旧 RepositorySectionFragment 调用路径
玻璃过度复杂掉帧或背景错层第一轮只 FakeGlass，不启用 snapshot降级到 Solid material

七、建议 ADR

ADR 摘要 可落 docs/adr
Decision:
导航栏将从 Activity 附属控件重构为 AppNavigationBarLayout + AppNavigationBarHost 组成的独立物理组件。

Context:
当前悬浮导航栏依赖 Activity 布局、BottomNavigationView 背景、Fragment 根 padding 协作，导致底色不一致、玻璃材质难以稳定实现、变体扩展需要多处修改。

Consequences:
1. MainActivity 只接入 Host，不直接操作导航栏 View。
2. 运行时通过 Context -> Policy -> Variant -> RenderPlan -> Commit 管线渲染。
3. 新增变体通过 VariantRegistry / Resolver / Renderer 接入。
4. 第一轮只实现 Solid 与 FakeGlass，不实现真 backdrop blur。
5. 旧实现分阶段迁移，直到验收通过后清理。

八、v5 结论

这份蓝图把前四版的概念压成实施计划。真正开始做时，不建议一次性实现完整变体系统；应该先按里程碑 1 到 5 建出稳定管线，再做 FakeGlass。

最小成功定义：MainActivity 变薄、主导航与仓库导航行为不回退、RenderPlan 可测试、inset 统一、未钉选分区可高亮。达到这一步，再进入玻璃材质深化。
还可以继续补的一项：如果要提交给未来维护者，应把 v5 再拆成 ADR + Issue 切片 + 测试清单三份正式文档。
