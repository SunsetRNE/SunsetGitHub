独立导航栏组件，不只是换个壳

上一版的问题是偏“方向”和“展示”，但真正难点在物理渲染边界：谁画背景、谁管理玻璃、谁发布 inset、谁持有菜单、谁负责降级。本版把这些边界补齐。

核心决策：导航栏必须成为一个 overlay 物理组件，内部拥有 backdrop、material、stroke、menu 和 touch zone；Activity 只接入 Host，Fragment 不再被导航栏实现细节污染。

一、上一版不完善在哪里

缺口

没有定义物理层级

只说了 AppNavigationBarLayout，但没有明确 backdrop、material、stroke、menu、touch zone 的绘制顺序和所有权。

缺口

没有状态矩阵

Docked、Floating、Hidden、Solid、FakeGlass、Glass、登录态、仓库态之间如何组合还不够清楚。

缺口

没有降级策略

玻璃在 Android 28 到 36 上不能按一个实现走，需要明确 fake glass、RenderEffect、snapshot 的切换条件。

缺口

没有生命周期边界

组件什么时候 attach NavHost、什么时候 release backdrop、什么时候重新计算 inset，需要写成契约。

缺口

没有迁移护栏

哪些旧类保留、哪些先不删、哪些行为必须先用测试锁住，还不够硬。

缺口

没有视觉验收

需要明确怎么判断“底色一致”和“玻璃成立”，否则很容易改成另一种错觉。

二、组件契约

把导航栏当成一个可渲染 surface，而不是 BottomNavigationView 的包装器。它的公开 API 应该稳定、少、明确。

AppNavigationBarLayout View contract
class AppNavigationBarLayout @JvmOverloads constructor(
    context: Context,
    attrs: AttributeSet? = null
) : FrameLayout(context, attrs) {

    fun render(state: AppNavigationBarState)

    fun setEventListener(
        listener: (AppNavigationBarEvent) -> Unit
    )

    fun attachBackdropHost(host: ViewGroup)

    fun setInsetsChangedListener(
        listener: (AppNavigationBarInsets) -> Unit
    )

    fun release()
}
AppNavigationBarHost Host contract
class AppNavigationBarHost(
    private val navController: NavController,
    private val navigationBar: AppNavigationBarLayout,
    private val destinationPolicy: NavigationBarDestinationPolicy,
    private val sectionPolicy: RepositorySectionDestinationPolicy,
    private val preferences: RepositoryNavigationPreferencesRepository,
    private val showMoreSections: () -> Unit
) {
    fun setAuthorized(value: Boolean)
    fun setFloatingEnabled(value: Boolean)
    fun onDestinationChanged(id: Int, args: Bundle?)
    fun refresh()
    fun release()
}
边界：View 只知道“怎么画”和“用户点了什么”；Host 只知道“当前应该是什么状态”和“事件该导航到哪里”；Policy 只知道 R.id 与规则映射。

三、物理渲染层级

这是悬浮和玻璃能否做稳的核心。组件内部必须有固定的层级顺序，后续所有材质都在这个顺序上替换。

Layer 0 Host Content
NavHost / Fragment 内容。组件不拥有它，但可以 attach 作为 backdrop 来源或 inset 应用目标。
Layer 1 Hit Slop
悬浮栏外扩触摸安全区。透明，但属于组件，避免圆角外点击穿透造成误触。
Layer 2 Backdrop
Solid surface、FakeGlass tint、未来 snapshot blur 或 RenderEffect 承载层。
Layer 3 Material
圆角裁剪、阴影、elevation overlay 控制、透明度和饱和度策略。
Layer 4 Stroke
Docked 模式是顶部 divider；Floating/Glass 模式是圆角边框和高光。
Layer 5 Menu
BottomNavigationView 或未来自绘 menu，负责 item、label、selection indicator。

五、玻璃能力分级

能力启用条件实现必须保证
Solid默认，所有设备主题 surface + stroke + shadow颜色与页面 canvas 一致，无透明错层
FakeGlass悬浮开启，所有设备半透明 tint + stroke + shadow + rounded clip稳定、低成本、无截图
RenderEffectGlassAPI 31+ 且性能允许RenderEffect / snapshot renderer可降级，滚动不掉帧
SnapshotGlass实验开关低频捕获 content host 区域并模糊生命周期可释放，不能常驻大 bitmap
重要：Android 的 RenderEffect 模糊 View 自身内容，不天然等于 iOS 式 backdrop blur。要真模糊背后内容，需要 snapshot 或专门 backdrop host。因此第一版实现 FakeGlass 更靠谱。

六、关键实现决策

Decision 1

Activity 采用 overlay root

NavHost 作为底层内容，AppNavigationBarLayout 作为底部 overlay。组件发布 inset，不再把底栏放进内容流。

Decision 2

先保留 BottomNavigationView

第一阶段不自绘 item。先把物理边界和状态模型做稳，再考虑完全自绘菜单以获得更强玻璃控制。

Decision 3

目的地策略纯 Kotlin

NavigationBarDestinationPolicy 和 RepositorySectionDestinationPolicy 不依赖 View，便于单元测试锁行为。

Decision 4

未钉选分区临时入栏

从 More 打开未钉选分区时，临时替换最后一个快捷槽，保证当前分区可见且可高亮。

七、迁移路线

1

加纯模型，不改 UI

新增 State、Event、Menu、Material、Insets、DestinationPolicy，并补最小单测。

2

加 AppNavigationBarLayout

内部先复制现有 BottomNavigationView 物理结构：backdrop、stroke、navView。旧实现暂时保留。

3

把 activity_main.xml 替换为 overlay 结构

用单个组件替代 nav_view_container、divider、navView，MainActivity 改为绑定组件。

4

HostController 改事件驱动

Host 生成 state，View 发 event。删除外部 menu.clear、inflateMenu、selectedItemId 直接操作。

5

迁移内容 inset

组件根据测量高度和 placement 发布 AppNavigationBarInsets，统一由 ContentInsetApplier 应用。

6

启用 FakeGlass

做圆角、stroke、高光、shadow、透明 tint。先验收视觉一致性，不做真 blur。

7

清理旧 surface 层

行为稳定后删除 MaterialBottomNavigationBarSurface、旧 Renderer/MenuSurface 或让它们成为组件私有实现。

九、第一轮不做什么

不要第一轮做真 backdrop blur。真模糊需要 snapshot 生命周期、滚动同步、内存释放、API 降级和性能保护。第一轮只完成独立组件、状态契约、FakeGlass 和 inset 统一。
不要同时自绘导航 item。继续用 BottomNavigationView 保住行为和可访问性。等物理组件稳定，再决定是否替换为自绘 menu。

十、最终判断

更完整的方案应该把“导航栏功能”和“导航栏材质”分开：功能由 Host + Policy + MenuModel 管，材质由 AppNavigationBarLayout + Renderer 管。这样悬浮、玻璃、底色一致性都落在一个独立物理组件里，而不是继续散在 Activity、Fragment 和多个 helper 中。

推荐执行顺序：先按 v2 做组件边界和 FakeGlass，达到底色一致；再考虑 RenderEffectGlass。这样路径更稳，返工概率小。
