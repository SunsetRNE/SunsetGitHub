Spec v3 · Variant System

把导航栏做成可新增变体的组件系统

v2 补了物理层级和玻璃路线，但还少了关键一块：变体如何处理、如何组合、如何新增、如何避免冲突。v3 把导航栏拆成“基础组件 + 变体解析 + 渲染策略 + 能力降级”。

目标是以后新增悬浮玻璃、紧凑模式、横屏模式、仓库临时分区、平板 NavigationRail、沉浸式编辑页等，不再改一堆 if，而是新增一个 Variant 或 Resolver。

变体分类解析链新增流程冲突规则
Docked / Solid / Main
Floating / Glass / Repository
Compact / Dense / Keyboard
Dark / Glass / API fallback

一、变体不是一个枚举，而是多个轴

不要做一个巨型 enum，例如 `FloatingGlassRepositoryCompactDark`。应该把变体拆成多个独立轴，最后组合成 `AppNavigationBarResolvedVariant`。

变体轴例子谁决定影响范围
PlacementVariantDocked / Floating / Rail / Hidden用户偏好、窗口尺寸、目的地规则布局位置、尺寸、内容避让
MaterialVariantSolid / Translucent / FakeGlass / RenderEffectGlass主题、设备能力、性能策略背景、透明度、描边、模糊
MenuVariantMain / RepositorySections / ContextualActions当前 destination 与业务上下文菜单项、选中态、事件输出
DensityVariantRegular / Compact / LabelHidden / IconOnly屏幕宽高、键盘、横屏、无障碍字体高度、label、item spacing
SurfaceVariantLight / Dark / HighContrast / DynamicColor主题与可访问性颜色 token、stroke、状态层
BehaviorVariantPersistent / AutoHideOnScroll / KeyboardHidden页面行为策略显示动画、隐藏规则、hit slop
核心：新增变体时优先判断它属于哪个轴。只有跨多个轴的体验，才新增一个 Resolver 或 Preset。

三、变体解析链

变体不应该散在 Host 里判断。Host 收集上下文，Resolver 链产出最终变体。

Variant Resolver Chain 顺序很重要
interface AppNavigationBarVariantResolver {
    fun resolve(
        input: AppNavigationBarVariantInput,
        draft: AppNavigationBarVariantDraft
    ): AppNavigationBarVariantDraft
}

class AppNavigationBarVariantPipeline(
    private val resolvers: List<AppNavigationBarVariantResolver>
) {
    fun resolve(input: AppNavigationBarVariantInput): AppNavigationBarResolvedVariant {
        val draft = resolvers.fold(AppNavigationBarVariantDraft.default()) { current, resolver ->
            resolver.resolve(input, current)
        }
        return draft.normalize().toResolvedVariant()
    }
}
解析器职责例子
DestinationVariantResolver由页面决定显示、菜单类型、强制隐藏登录页 Hidden，仓库页 RepositorySections
PreferenceVariantResolver应用用户设置开启悬浮则 Docked -> Floating
WindowVariantResolver根据屏幕、横屏、平板调整宽屏可切 Rail，低高度切 Compact
CapabilityVariantResolver根据 API 和性能降级RenderEffectGlass -> FakeGlass
InteractionVariantResolver根据键盘、滚动、选择模式调整键盘弹出 Hidden 或 Compact
AccessibilityVariantResolver根据字体缩放、对比度调整大字体禁用 LabelHidden，强化 stroke

四、变体注册与新增机制

新增变体要通过注册表进入系统，而不是直接改 View 的 when。注册表负责把 variant 映射到 renderer、dimension、token 和 fallback。

Variant Registry 集中注册
class AppNavigationBarVariantRegistry(
    val placementRenderers: Map<PlacementVariant, PlacementRenderer>,
    val materialRenderers: Map<MaterialVariant.Kind, MaterialRenderer>,
    val menuRenderers: Map<MenuVariant.Kind, MenuRenderer>,
    val fallbackRules: List<VariantFallbackRule>
)
Fallback Rule 可降级
data class VariantFallbackRule(
    val whenRequested: VariantMatcher,
    val ifUnsupported: CapabilityMatcher,
    val replaceWith: VariantPatch,
    val reason: String
)

五、新增一个变体的标准流程

1

判断变体轴

先问：这是 placement、material、menu、density、surface、behavior，还是多个轴的 preset？不要默认新建大枚举。

2

定义数据模型

新增小而独立的 variant data class，例如 `MaterialVariant.Glass(radius, tintAlpha, strokeAlpha)`。

3

注册 renderer

在 registry 中注册该变体对应 renderer。View 只查 registry，不直接知道所有变体。

4

定义 fallback

为低 API、低性能、深色、高对比度、大字体定义降级路径。

5

加入 resolver

只有当变体需要自动选择时才加 resolver；如果只是可手动指定，不要污染解析链。

6

补状态矩阵和测试

至少覆盖该变体与 Docked/Floating、Light/Dark、Main/Repository 的组合。

六、变体冲突处理

冲突规则原因
Hidden + 任意 MaterialMaterial 不渲染，inset = 0隐藏态不应保留视觉副作用
Rail + Bottom menu density切换到 RailDensity横向 BottomNavigationView 尺寸规则不适用
Glass + API < 31RenderEffectGlass -> FakeGlass避免不可用 API 和伪真模糊
Compact + 大字体Compact -> Regular，必要时 LabelHidden -> LabelVisible无障碍优先级高于视觉密度
Floating + 键盘显示按页面策略 Hidden 或 Compact避免遮挡输入和 IME 动画冲突
Repository 未钉选当前分区临时注入当前分区，占用最后一个快捷槽保证当前态可见且可高亮

九、第一轮实现范围

范围包含不包含
PlacementDocked、Floating、HiddenRail 只预留模型
MaterialSolid、FakeGlassRenderEffectGlass 只预留接口
MenuMain、RepositorySectionsContextualActions 暂不做
DensityRegular、Compact完全自绘 item 暂不做
ResolverDestination、Preference、CapabilityAutoHideOnScroll 暂不做
重点：v3 的价值不是第一轮做很多变体，而是让第一轮实现天然能接住后续变体。

十、验收标准：新增变体不改核心 Host

以后新增一个导航栏变体，理想情况下只需要新增模型、renderer、fallback、resolver 测试，而不是改 MainActivity 或 AppNavigationBarHost 的核心流程。

完成定义：当 `AppNavigationBarHost` 只负责收集 input、调用 pipeline、处理 event，而所有视觉变化都由 variant registry + renderer 承接时，这个组件才算真正可扩展。
